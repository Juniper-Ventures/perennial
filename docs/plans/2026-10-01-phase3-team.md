# Perennial Phase 3 — A team of perennials

**Goal:** several named perennials run side by side on the same machine. Each has its own charter (builder, researcher, ops), and they share the same todo sources without doing the same task twice. Todos from Airtable join the queue.

**Architecture:**
- Each perennial is one config, one home dir and one supervisor process.
- Coordination happens through a small shared SQLite file, `claims.sqlite`. Before a run, a perennial claims the task id. The first claim wins. Task ids are deterministic (`sha256(source, ext_id)`), so all perennials compute the same id for the same todo. If a run fails, the claim is released so another perennial can try. A parked task keeps its claim.
- Airtable todos arrive as an exported Markdown checklist. A host-side command writes it; the perennials read it like any other Markdown source.

## Contracts

- `Claims(path)`: `claim(task_id, owner) -> bool`, `release(task_id, owner)`, `owner_of(task_id) -> str | None`. Each call opens a short connection, so separate processes are safe (SQLite locking, `INSERT OR IGNORE`).
- Config: `claims = "/Users/Shared/perennial/claims.sqlite"`. This is optional; without it, there is no coordination.
- Supervisor `_run_one`: walk the ready tasks in order. Run the first one this perennial can claim. A task that another perennial owns gets the status `claimed`. Release the claim on a failed run.
- Triage uses the charter, so each perennial says `skip` to work outside its role.
- `airtable.records_to_markdown(records, done_values, owner_email=None) -> str`:
  - One `- [ ]` line per open record: the task text, the deadline and the next step on an indented line.
  - Records with a done status, or owned by someone else when `owner_email` is set, are left out.
- `perennial export-airtable --base B --table T --out FILE [--owner-email E]`: reads `AIRTABLE_PAT` from the environment and writes the file atomically. This is a host-side command.
- `examples/` has three configs: `builder.toml`, `researcher.toml` and `ops.toml`.

## Tasks

1. `claims.py` + tests: first claim wins across two instances; release frees the claim; a release by a non-owner is ignored.
2. Config key `claims` + test.
3. Supervisor claim integration + tests: two supervisors on one source never run the same task, and a failed run releases the claim.
4. `airtable.py` + tests: filter, format, owner filter, Markdown special characters in the text.
5. CLI `export-airtable`; three example configs; docs (`docs/team.md`).
6. Live check: two perennials with the same Markdown source each take a different task.

## Result (1 Oct 2026)

- 75 tests pass.
- Live check: Forge and Sage shared one Markdown source with one coding todo and one research todo, plus one `claims.sqlite`.
  - Forge built `reverse_words.py` with a passing test and skipped the research todo as outside its role. Cost: $0.22.
  - Sage wrote a 113-word cited explanation (sqlite.org/wal.html and two pragma pages). Cost: $0.34.
  - Sage's triage also wanted the coding todo, but Forge had already claimed it. Sage marked it `claimed` and did not run it. Both safeguards worked: the role filter in triage, and the claims as a backstop.
- The Airtable export ran live against the real `TO DO` table and returned 8 open items.
